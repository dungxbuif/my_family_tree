# Multi-family Access, API, and MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the application to multiple family trees per user, disable public registration, add exact-email membership/person linking, and expose user-bound REST/MCP credentials that enforce current per-tree permissions.

**Architecture:** System account lifecycle is separate from per-tree membership. Every family-data operation resolves an authenticated user and validated Family Tree, then enforces owner/editor/viewer permissions through shared authorization helpers. API keys authenticate as their owning user and never carry broader or stale tree permissions.

**Tech Stack:** Next.js 16 App Router, TypeScript, PostgreSQL/`pg`, Bun test, `@modelcontextprotocol/server`, Zod 4.

**Spec:** `docs/superpowers/specs/2026-11-19-api-mcp-design.md`

## Global Constraints

- Follow `GLOSSARY.md` and ADR 0001; System User, Person, Tree Membership, and Super Admin are distinct concepts.
- No public registration, account search/autocomplete, email delivery, invitation token, or pending invitation.
- Owners add only an existing active System User by complete trim/lower-normalized email.
- Each family tree always has at least one Owner; each Person and System User can have at most one Person Link per tree.
- Exact email may create a missing Person Link but never silently replace one.
- API keys belong to users; every call re-evaluates current membership for the requested tree.
- Follow `docs/design/DESIGN.md`; new UI is mobile-first at 320–430px, has 44px targets, safe-area spacing, no horizontal overflow, and scales to desktop without a second visual language.
- Production migration must preserve all existing records and access, run transactionally through the declared deployment migration path, and provide preflight, backup, verification, and rollback instructions.

## Review Focus

- A forged tree ID, stale selected-tree cookie, or object ID from another tree never reads or mutates data.
- Concurrent owner demotion/removal cannot leave a tree without an Owner.
- Exact-email add does not reveal whether partial or candidate emails exist.
- Updating email on an already linked Person never transfers the link; collisions fail deterministically.
- Production backfill is rerunnable/idempotent, preserves row counts, and fails before mutation on normalized-email collisions or invalid legacy references.
